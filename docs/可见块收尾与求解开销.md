# 可见块收尾与求解开销

2026-10-15，版本0.11.7。保留原PC搜索、纯四行及4＋4＋6 DPC。新增收尾实验默认关闭；求解过程减少文件读写已启用。以下均为离线规划测试，没有新增原生Blitz局，不能据此宣称原生finesse已解决或实际达到某个PPS。

## 不知道下一块，也可能已经能保证本次PC

原搜索把最后一次Hold换入后留在Hold里的块也算进需要预测的范围。如果最后一块来自已知Hold，而未知active只被存入Hold，就无需猜它的身份；它没有被落在棋盘上。

真实旧680块局在第4块前的可见状态：Hold是T，active及五个Next是`IZSJZL`，棋盘从上到下为：

```text
_______JJJ
_________J
_______LOO
_____LLLOO
```

棋盘已有12格，还需要7块完成四行PC。六个可见来块加Hold正好7块；地面180旋转求解验证能全部放置，最后Hold记为`?`。这个问号表示携带块未知，绝不是可放置方块。程序逐步检查每个落地块的来源和身份都已知；真正执行到最后换Hold时，还要从当下画面确认未知active。后续规划再用新观测绑定它。这里引用旧日志中的当时可见状态作为回归例，不给在线程序传历史未来队列。

CLI选项`--observed-finish-first`、API参数`observed_finish_first=true`允许先尝试这类完整收尾。最多占35毫秒或本次总预算35%，取较小者；失败或超时再用原预测方法。超时仅表示未搜索完，不能当成没有PC。`visible_finish_stats.plans`是找到方案次数，不是最终实测PC次数。

## 随机配对结果

每个case由SystemRandom新生成；同一case的不同方法共用来块作配对比较。规划器只得到active、Hold、指定Next和此前已观察信息。整个未来队列只存在于离线模拟器中，不交给规划器，也不输入游戏。每次700块，并逐块独立核对落点可达、消行与棋盘一致。

第一批：六个Next、4个case，每种策略各4次关闭和4次开启，共16次全部完成700块。使用文件优化之前版本，不能与后面的五Next批合并。

| 策略 | 收尾实验 | 平均消行分 | 平均PC | 平均额外参考输入 |
|---|---|---:|---:|---:|
| balanced | 关 | 2,480,937.5 | 51.5 | 163 |
| balanced | 开 | 2,512,425 | 52.75 | 167.75 |
| strict | 关 | 1,842,650 | 38.25 | 0 |
| strict | 开 | 1,872,250 | 38.5 | 0 |

两种策略各2个case增分、2个减分。balanced共110次试探、20个方案、86次未完成；strict共136次试探、19个方案、106次未完成。清分均值增加约1.27%和1.61%，但预算压力与额外输入仍存在。

第二批：五个Next、2个新case，初始active分别S、T；包含下面的文件优化。8次全部700块，无几何错误，模型Level16。

| 策略 | 收尾实验 | 平均消行分 | 平均PC | 平均额外参考输入 | 700块规划墙钟秒 |
|---|---|---:|---:|---:|---:|
| balanced | 关 | 2,282,100 | 47.5 | 135 | 14.3265 |
| balanced | 开 | 2,482,650 | 52 | 144.5 | 12.0495 |
| strict | 关 | 1,455,800 | 26 | 0 | 19.659 |
| strict | 开 | 1,540,000 | 28 | 0 | 19.6105 |

本批两case均增分，balanced均值+8.79%、strict+5.78%。balanced58次试探找到24方案、5次未完成；strict97次试探找到20方案、8次未完成。样本只有两个，balanced额外输入还增加约7.04%，因此暂不改默认。模型0额外输入也不等于原生0faults。这些分数不含下降分；没有模拟真实输入时序和重力，墙钟也不是完整游戏时长。

## 减少每次搜索的文件开销

常驻Java求解器在不保存单次搜索文件时直接接收10×2／4／6的棋盘字符串，取消临时目录、field.txt、日志与result.json写入。保留逐局JSONL、截图、原生录像和刷分尝试记录；普通用户要求保存的求解仍按原方式保存。

两组离线几何回归例各20对，交替运行保存模式与不保存的直接传递模式，提前暖机3次，80次解法的完整步骤全部一致：

| 回归例 | 保存模式中位耗时 | 直接传递中位耗时 |
|---|---:|---:|
| 单个O收尾 | 4.5106 ms | 2.35595 ms |
| 七块收尾 | 30.84025 ms | 27.61870 ms |

这里包含取消保存日志和JSON的收益，不能称为纯通信收益，也没有测原生PPS。原始数据`output/solver-inline-overhead-benchmark.json`；脚本`scripts/benchmark-solver-overhead.py`。新增测试检查无目录／文件写入、与保存模式完全同解、坏输入不污染下一次常驻查询。完整141项测试通过。

## 预览数与首袋条件必须分清

旧原生680块录像与本项目原版Blitz配置为五个Next。早期离线六Next实验是另一信息条件，不能直接当作原版Blitz成绩。因此新基准可选`--next-count 5|6`，初始观察集合也随之改变，五Next不会偷偷获得第七个active来源。

历史世界纪录回放的options含`no_szo=true`；本项目旧680块原生回放没有该字段。社区作者的[Piece RNG说明](https://github.com/lemoncove/tetrio-bot-docs/blob/master/Piece_RNG.md)描述NoSzo为跳过首个S/Z/O，而不是重抽完整首袋。当前全部首块离线七袋和旧排除S/Z/O的条件样本，都没有模拟这种跳块规则；不能把它们视为该选项的原生分布，更不能据一份历史录像认定今天客户端的默认值。

当前观察一致性和来源周期按从来源0开始的完整七袋计算。如实际配置跳过首块，需要明确袋相位后再推断，不能简单取消重复方块检查。尚未验证或改写这一规则，也没有给当前Blitz配置添加NoSzo；需要实际进入客户端后核对当前设置／录像。首块为S的本批案例仅说明离线完整七袋测试覆盖该起手。

[FOUR的DPC资料](https://four.lol/perfect-clears/dpc/)展示按不同携带块选择地形；有些地形覆盖率100%，也有带T-spin的较低覆盖方案。单一地形的覆盖率不能自动成为“高重力、标准按键、整局持续循环”的成功率。下一步应分别验证袋相位、真实五Next、可见收尾与少按键地形的共同条件，然后再做独立随机原生测试。
